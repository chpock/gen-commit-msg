## Independent implementation review: verified findings

1. **Late statistics response ID (P2): accepted and fixed.** The native RPC reference requires response-ID correlation because command handling is asynchronous. A deterministic fixture withholds `stats-1` until `prompt-2` arrives after the telemetry timeout. Before the fix, `TestPiLateStatisticsResponseIDs` failed for both successful and rejected late responses: the logger used the active exchange ID. The response logger now records the wire `id` and separate `exchange_id`. Both late-response variants pass and preserve candidates, a single telemetry-timeout log, second-attempt statistics and completed reaping.
2. **Duplicate tool-call `id`: accepted and fixed.** Before the fix, `TestPiToolCallDiagnosticIDs` observed the exact raw JSON diagnostic with both `"id":"prompt-1"` and `"id":"fixture-tool"`; this verifies the second opinion's initially inferred consequence. Streamed tool metadata now uses `tool_call_id` and `tool_name`, preserving the prompt ID. The regression checks the raw line as well as decoded fields so duplicate keys cannot be hidden by map decoding.
3. **Bounded stderr documentation: accepted and clarified, behavior retained.** Direct inspection of `process.stop` confirms the last 16 KiB is logged on successful runs at DEBUG, escalating to WARN/ERROR as before. README/product/UX now explicitly distinguish that opaque tail from payload-free activity summaries and full live TRACE stderr. UX also distinguishes terminal log output from TUI/commit rendering.
4. **Late-response coverage gap: accepted and closed** by the two deterministic cases in item 1; no sleep-based assumption about arrival ordering is used. Exact statistics-query counts at INFO versus DEBUG/TRACE were tightened as well.
5. **Mixed DEBUG field styles/bare optional events: rejected as defects.** Wire-style numeric/state metadata is readable; tool identity now follows existing snake_case naming where collision mattered. Bare optional events expose activity without leaking their payload; full records remain available at TRACE. A global log-schema cleanup or broader disabled-feature handling is not required by this request.
6. **Slow-log-sink claim: corrected.** The second opinion stated stdout draining is unaffected by synchronous TRACE writes. `process.go` logs stdout directly before enqueue, so a slow shared sink can slow either stream, not just stderr. This is the ordinary synchronous logging trade-off of full TRACE, not evidence for adding buffering or dropping records. TRACE volume/sensitivity and destination selection remain documented.

No candidate-loss, generation-deadline, cleanup, isolation or output-contract defect was reproduced. Remaining maintenance signals concern test dispatch/size, not a behavior failure; a fixture-framework refactor is outside this logging task.
